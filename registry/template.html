Silent Failures Registry

Twenty ways scientific and ML code returns a wrong answer without raising an error.

Every plate names one class of defect, where it hides, what it looks like from the outside, how it works, how to detect it, and the test that would have caught it. Every plate is anchored to a specimen: a public pull request or issue where the pattern was found and fixed, with the numbers reported there. Thirteen classes have a static detector in the companion tool, sfradar; seven are documented for manual review.

How to use it

As a review checklist before a result leaves the lab: walk the twenty plates against the pipeline and write down, for each, 'checked', 'not applicable' or 'not checked'. The honest third column is the point.

As a screening tool: run sfradar on the repository; it ranks where to look first and hides its own low-confidence guesses.

How to cite

Coiffard-Donaty, A. (2026). Silent Failures Registry, v0.1. https://github.com/AxelNoun

Contributions: a new plate needs a public specimen with numbers; a fix to a plate needs a reference or a reproduction.

What it is not

Not a taxonomy of all software bugs, not a security catalogue (see CWE for that), not a proof that a codebase is correct. It is the written-down method of one practitioner, with its evidence attached, so that others can check it and extend it.

Quotes from maintainers are verbatim from the linked pages. Latin plate names are mnemonics, not a formal nomenclature.
